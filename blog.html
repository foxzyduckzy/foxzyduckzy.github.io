v1.4: Agent mode is here

Until now, working with Loopable8 meant a conversation: you ask, it answers, you apply. That loop is great for questions — and too slow for tasks. Agent mode closes the gap.

Task in, reviewed change out

Type /agent make send() resilient to stream drops and the agent produces a plan first: which files it will touch, what it expects to change, roughly how long it will take. Nothing runs until you approve the plan.

Execution happens file by file with live progress. When it's done, the agent runs whatever checks it can find — analyzer, tests — and reports the result honestly, including failures. Every edit lands as an inline diff. Your codebase, your call.

Limits that respect your attention

Agent runs are bounded: three retries, explicit scopes, and a hard rule that destructive operations (deletes, force-pushes) always stop for confirmation. AI that surprises you is AI you stop trusting.

Every plan includes a weekly credit allowance; paid plans give you more. Update to v1.4 and try it on your ugliest file.

The Loopable8 ecosystem: what's coming and when

One question keeps arriving from every channel: "is Loopable8 just the coding assistant?" No — but we'd rather under-promise. Here's the honest roadmap.

Shipped: the AI Coding Assistant

Our only completed product today, and the foundation everything else builds on. It gets the majority of our engineering time and a release every few weeks.

Next: AI Chat (targeting Q4 2026)

The original Loopable8 experience, rebuilt on the v1.4 engine: grounding search, persistent memory, voice, full run settings. If you liked the studio-style chat, this is that — sharper.

In research: AI Studio

Image, video and voice generation with run-control depth: seeds, styles, reference assets, reproducible outputs. We treat generations like builds, not slot machines. No date yet — it ships when that bar is met.

Prototype: the AI-native Game Dev Studio

The most ambitious piece: physics, gameplay loops, shaders and level logic, generated and debugged with engine-aware context. Early prototypes are promising on C# and C++ game code. Pro members get the first beta invites.

Every product shares one account, one license, one design language. That's the whole strategy: a studio, not a bundle.

How we wired MCP into a Flutter app

v1.2 shipped a real Model Context Protocol client — not a wrapper around a wrapper. A few notes for anyone building the same thing.

JSON-RPC without the ceremony

MCP is JSON-RPC 2.0 over stdio or HTTP. Our client is a few hundred lines of Dart: spawn the server process, negotiate capabilities, list tools, forward calls. The hard part isn't the protocol — it's lifecycle. Servers crash, hang and leak; we supervise every process and restart with backoff.

Function calling as the bridge

Tool schemas from MCP become Gemini function declarations almost 1:1. When the model emits a function call, we route it to the right server, await the result, and stream it back into the conversation. Every call is logged in the task panel — silent tool use is how trust dies.

What we'd do differently

Start with the marketplace UI sooner. Config-file-only tools meant only power users touched MCP in v1.2; the v1.4 marketplace tripled adoption in a week.

Why we rebuilt Loopable8 around code

Loopable8 started life as a Google AI Studio-style chat app: model picker, temperature slider, system instructions, the works. People liked it. But the usage data told a clearer story: the longest, most engaged sessions were all about code.

So we made the call — rebuild the product around the editor. The chat didn't disappear; it moved into the right-hand panel where it belongs, next to the code it's talking about.

What stayed

The run settings philosophy survived intact: the panel is the source of truth, and the engine reads exactly what you set. That idea turned out to matter even more for coding, where reproducibility is the difference between a tool and a gimmick.

The studio-style chat returns as a standalone product — see the roadmap post.
